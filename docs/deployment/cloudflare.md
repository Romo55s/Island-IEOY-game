# Cloudflare deployment

The game is a single Cloudflare Worker application. It serves the built frontend and handles `/api/*` plus `/parties/*` multiplayer traffic. `GameRoom` is a SQLite-backed Durable Object; each named room coordinates the connected players and WebSocket messages.

## Current production deployment

- URL: <https://ieoy-game.ieoy-game.workers.dev>
- Account `workers.dev` prefix: `ieoy-game`
- Worker: `ieoy-game`
- Durable Object namespace: `GameRoom` (SQLite)
- Verified after deployment: HTTPS homepage, `/api/health`, and character manifest all returned HTTP 200.
- Observability: persisted invocation logs, Worker Issues, and full log sampling are enabled; query strings are redacted. Distributed traces are not enabled.

## Current project setup

- `cloudflare.config.ts` declares Worker `ieoy-game`, static assets, the `GameRoom` SQLite Durable Object, and its `GAME_ROOM` binding.
- `worker/index.ts` serves the health and session endpoints and routes authorized WebSocket upgrades to PartyServer.
- The first successful `cf deploy` provisions the declared Durable Object namespace. No separate Pages project or multiplayer server is required.
- `npm run dev` runs the Cloudflare local development path; use `npm run build` to produce the deployable bundle.

## Static asset caching

`public/_headers` applies bounded caching to stable public media while allowing HTML and root paths to revalidate. Built `/assets/*` files are cached for one year as immutable because the bundler fingerprints their filenames. Public `/images/*` and `/models/*` files are cached for one day; replacing a model or image at the same URL can take up to a day to appear in a returning browser's cache. The character manifest is explicitly left on revalidation so new URLs become visible promptly. For immediate media updates, use a new filename or versioned URL. API and multiplayer responses are generated by the Worker and should remain uncached.

Portrait GLBs are requested only when their portrait enters the visible UI viewport. The rest of the character cards use their initials until the model finishes loading. This reduces first-load bandwidth; models already downloaded may remain in Three.js's in-memory GLTF cache for the current page session.

## One-time Cloudflare setup

1. Create or sign in to the Cloudflare account that will own the game.
2. Enable the `workers.dev` subdomain in that account if you do not have a custom domain ready.
3. Authenticate the local CLI with `cf auth login`, then confirm the selected account with `cf auth whoami`.
4. Run `npm run build`, `npm run check:bundle`, and `cf deploy --prebuilt --mode production --dry-run` to validate the bundle without publishing it.
5. Run `node scripts/check-deployment-approval.mjs` before publishing. The current model and voice manifests are approved for this game deployment; the asset register records the scope of that permission. Then run `cf deploy --prebuilt --mode production` to publish the Worker, static game assets, and Durable Object binding together.

## GitHub Actions deployment

`.github/workflows/deploy-cloudflare.yml` is a manual-only production workflow. In the GitHub repository settings:

1. Add a `production` environment. Add required reviewers there if you want GitHub to pause for a second approval before production deployment.
2. Add environment secrets named `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Use a narrowly scoped API token that can deploy Workers and provision the bindings in this project.
3. Open **Actions → Deploy to Cloudflare → Run workflow** after the asset approval gate passes.

The workflow builds once, checks the deploy bundle, validates it with a Cloudflare dry run, then deploys that same prebuilt output. It does not deploy on every push.

## Multiplayer behavior

The browser should use the same origin for the app and multiplayer endpoints. The frontend's `/api/...` and `/parties/game-room/...` requests are served by the Worker, so session creation, tickets, and WebSocket upgrades do not need a separate CORS allowlist or a second host. Keep the existing ticket validation: clients obtain a short-lived session ticket before opening the room WebSocket.

After deployment, check `GET /api/health`, then create a session and connect two browsers using the normal game flow. For live diagnostics, use Cloudflare Worker logs in the dashboard or the project's supported `cf` logging commands.

For production errors, open **Workers & Pages → `ieoy-game` → Observability → Logs** and filter for errors or `$workers.outcome = "exception"`. Issues are enabled for grouped failure detection. Cloudflare retains persisted Workers Logs for up to seven days.

## Asset approval gate

Cloudflare-hosted static files are publicly retrievable by URL. The owner approved deployment of the current game build on 2026-11-23; all 16 model entries and the voice manifest are marked approved for this deployment. `scripts/check-deployment-approval.mjs` checks those manifest flags before the deploy workflow uses Cloudflare credentials.
